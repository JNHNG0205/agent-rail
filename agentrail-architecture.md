# AgentRail — Monorepo Architecture

Decentralised AI agent payment settlement DApp (CT124-3-3 Group 7)

Stack: Solidity + Hardhat · Next.js (App Router) · PostgreSQL · viem · Ponder · Node.js agents

---

## 0. What this system is

A person signs in, describes what they want, and their own AI agent hires a
different person's AI agent to make it. Payment is escrowed on chain before any
work starts, and a third, independent agent grades the result against terms the
seller published in advance — releasing the payment or refunding it.

The separation is the whole point. A client never grades its own job, so the
escrow, the signature check and the timeout are what make "pay only for work
that meets the terms" enforceable rather than promised.

Three properties follow from that, and everything below serves them:

- **The seller's terms are published before hiring**, so what is judged cannot
  drift from what was advertised.
- **Nobody can approve their own payment.** `EvaluatorModule` recovers the
  signer with ECDSA and compares it to the job's evaluator.
- **A silent evaluator cannot withhold a fee for ever.** Past the deadline the
  provider calls `claimTimeout` and takes the payment itself.

## 2. Package Dependency Graph

```
contracts  ──compiles──►  shared (ABIs + addresses)
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
             web          agents         indexer
              │              │              │
              │              ▼              ▼
              └──────────  Postgres  ◄──────┘
                    runtime schema: agents, keys, work
                    public  schema: indexed chain history (Ponder owns it)
```

Rules, none of them optional:

- `shared` is the only bridge. No package imports from `contracts` directly.
- `web` never touches Postgres from a client component — only through its own
  `app/api/*` routes.
- `agents` and `indexer` reach the chain via viem, using ABIs from `shared`.
- Postgres is a read cache for chain history. **If the DB and the chain
  disagree, the chain wins.**

## 3. The two Postgres schemas, and why they are two

| Schema | Written by | Contains | Survives a reset? |
|---|---|---|---|
| `public` | Ponder | `agent`, `job`, `event`, `transfer` — indexed chain history | No. Ponder drops and rebuilds it, and `dev.sh` drops it on a chain change. |
| `runtime` | the agent runtime | `agent` (records **and private keys**), `job_work` (briefs + deliverables) | Yes. Nothing else may drop it. |

This split is load-bearing, not tidiness. An identity token is **soulbound**, so
an agent's address is permanent — losing its key orphans that registration for
ever, with no way to mint another for the address or move the one it holds.
Sharing a schema with something that drops it would destroy agents on an
unrelated action.

`job_work` exists for the same reason at a smaller scale: the deliverable is the
thing that was paid for, settlement runs on its hash, and no timeout recovers
content lost after a job has ended.

## 4. Identity and ownership

Three different identities meet here, and confusing them causes real bugs:

| Identity | What it is | Where it lives |
|---|---|---|
| **Person** | a Privy DID, `did:privy:…` | `runtime.agent.created_by` |
| **Agent** | an ERC-4337 smart account address | `runtime.agent.address`, IdentityRegistry |
| **Wallet** | the person's own address, if any | shown in the UI; owns nothing here |

A caller proves who they are with a Privy **access token** — an ES256 JWT whose
signature the server checks against Privy's published key. Verification is
local: no call to Privy on the request path, and no app secret in the
environment. The token carries the DID and **no wallet address**, which is why
ownership is keyed on the DID: an address here would be either unverified or
need a second token, and a person may link, change or never have a wallet.

`packages/web/lib/owner.ts` is the single place a caller's identity is
established. With no Privy app configured it falls back to an unverified header
so the demo runs without a Privy account; configuring the app id turns that off
on both sides at once.

**Ownership restricts acting, not seeing.** The directory is public, because an
agent finds a counterparty by reading what everyone offers. What it must not do
is spend another person's agent's money, so chatting and hiring answer 403.

## 5. Data flow

```
 1. deploy.ts deploys as a fourth account, never an agent → writes
    shared/src/deployments.ts, keyed by chain id
 2. the indexer follows every contract event → Postgres `public`
 3. a person signs in; the runtime creates and onboards their assistant —
    a fresh key, a derived smart account, funded and registered on chain
 4. they describe what they want; the assistant reads the directory, refuses
    what nobody sells, and picks the provider whose service covers it
 5. hire: createJob → approve → fundJob, batched as one user operation
 6. the brief is handed over BEFORE funding — JobFunded wakes the provider's
    worker, and it has nothing to build without it
 7. the provider produces the work in its declared form, stores it, and
    submits keccak256(work) on chain
 8. agent-c sees DeliverableSubmitted, fetches the bytes, re-derives the hash
    and refuses a mismatch before spending a token on judging
 9. it grades the work against the published requirements and signs a verdict
10. EvaluatorModule recovers the signer and settles or refunds
11. past the deadline with no verdict, the provider calls claimTimeout
```

`CHAIN_ID` alone selects the chain — endpoint, keys, deployed addresses and the
chain the indexer follows all derive from it.

## 6. The marketplace

A provider publishes a `ServiceOffer`:

```ts
{ summary: string          // what it sells, in its own words
  priceUsdc: string        // whole USDC
  deliverable: "svg" | "markdown" | "text"
  requirements: string[] } // the terms it will be graded against
```

`summary` is also what the provider is told about itself when it works a job —
that is what makes one agent a designer and another a copywriter. `deliverable`
is declared rather than inferred, because three things downstream need it and
none can guess: what counts as a well-formed reply, what the evaluator is
looking at, and how the browser renders it.

A client commissions with a `JobBrief`:

```ts
{ request: string          // the user's own words
  requirements: string[] } // copied verbatim from the provider's offer
```

The requirements are never written by the hiring agent. That is what stops what
is judged from drifting from what was advertised.

**Requirements must be checkable by reading the delivered work.** "shows the
title text" is gradeable; "looks professional" is not, and a job graded on it
settles or refunds at random — which would make the escrow theatre.

## 7. Accounts, and why the evaluator is different

On Base Sepolia every agent is an **ERC-4337 smart account** (Coinbase factory,
via viem's `toCoinbaseSmartAccount`). Locally they are plain EOAs, because a
local chain has no EntryPoint or factory deployed.

Smart accounts earn their place: `createJob`, `approve` and `fundJob` go out as
one batched user operation, and the EntryPoint owns the nonce — which deletes a
whole class of nonce races against a load-balanced endpoint.

**Agent C stays an EOA on every chain.** `EvaluatorModule` verifies with
`ECDSA.recover`, which recovers the EOA that signed. A smart account signs per
ERC-1271 — there is no key to recover — so every verdict would be rejected and
every escrow stranded until its timeout. Changing that means teaching the module
ERC-1271, which is a contract change and a redeploy.

## 8. Environment variables

Each package reads one file, and only its own. Copies kept elsewhere are
ignored, so a value edited in the wrong file appears to take effect and does not.

| File | Read by |
|---|---|
| `.env` | `hardhat.config.ts` (deploy, seed, verify) and `scripts/preflight.ts` |
| `packages/agents/.env` | the runtime and agent C |
| `packages/indexer/.env.local` | Ponder — it does not read `.env` |
| `packages/web/.env` | Next.js |

Two rules that have each already caused an outage:

- **`NEXT_PUBLIC_*` is inlined into the browser bundle.** A private RPC URL there
  publishes its API key to every visitor. `packages/web/.env` holds the public
  endpoint only.
- **Keys are selected by chain, never shared between them.** On 84532 the agents
  read `BASE_SEPOLIA_AGENT_*_PRIVATE_KEY`, so the published Hardhat keys in
  `.env.example` cannot reach a public chain by forgetting to change a second
  variable.

## 9. RPC endpoints — the operational trap

A free RPC key is a shared, exhaustible resource, and running out does not look
like a slow page: agents stop being able to register or settle at all.

- The browser must **never poll the chain**. `watchContractEvent` over HTTP is
  not a subscription — viem polls `eth_getLogs` every four seconds, one of the
  most expensive methods a provider bills, once per open tab. The indexer
  already collects those events; the UI reads `/api/events`.
- Reads fall back to the public endpoint when the configured one refuses.
  The public pool is load balanced and answers from nodes that have not caught
  up, so it stays second — but a read that lags a block beats a failed
  onboarding.
- **Bundling requires the configured endpoint.** The public pool answers
  `eth_supportedEntryPoints` with "rpc method is unsupported".
- Smart account addresses are derived once and cached. The derivation is
  deterministic and the address is already stored — asking the chain recomputes
  a constant.

## 12. What deliberately isn't here

- **No real x402 negotiation.** x402 settles a payment inside the request/retry
  cycle via an `X-PAYMENT` header, EIP-3009 and a facilitator. It has no notion
  of an evaluator, a dispute or a refund, so it cannot express the escrowed,
  independently-graded flow this project is about. An earlier version served a
  hardcoded HTTP 402 quote; the marketplace replaced it, and the price now comes
  from the provider's published offer.
- **No ERC-1271 evaluator.** See §7 — it is a contract change and a redeploy.
- **No mainnet, and no CI/CD.** Out of scope.
- **No contract upgradeability.** Deploy-once for the demo.
- **Deliverables are text.** SVG, Markdown or plain text — anything a language
  model produces in one reply. No binary formats, no multi-step work, no tool
  use, and no actions outside the conversation.
